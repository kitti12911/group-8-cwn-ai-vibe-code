## 3. ผลก่อนแก้ · การทดลองถอดกลไกออก

เว็บผ่านตั้งแต่รอบแรก ทีมจึงต้องพิสูจน์ย้อนกลับว่า **ถ้ากลไกหาย test จับได้จริงไหม** โดยแก้ 2 จุดชั่วคราว (ทำใน working tree แล้ว `git checkout --` คืน ไม่ commit)

| ไฟล์ | ของจริง | ตัวทดลอง |
| --- | --- | --- |
| `backend/internal/store/orders.go` | `UPDATE products SET available = available - $2 WHERE sku = $1 AND available >= $2 RETURNING available` | `SELECT available …` แล้วค่อย `UPDATE … SET available = available - $2` (check-then-insert) |
| `backend/internal/store/schema.sql` | `available int NOT NULL CHECK (available >= 0)` | `available int NOT NULL` (ถอดด่านสุดท้าย) |

## 4. ต้นเหตุ

```text
เวลา →
  คำขอ A:  SELECT available (เห็น 1) ✅ ─────────── UPDATE available = 1 − 1 = 0 ✅ COMMIT
  คำขอ B:        SELECT available (เห็น 1) ✅ ─────────── UPDATE available = 0 − 1 = −1 ✅ COMMIT
                 ↑ ทั้งคู่เห็นว่ายังมีของ เพราะยังไม่มีใคร COMMIT
```

ที่ isolation level `READ COMMITTED` (ค่าตั้งต้นของ PostgreSQL) คำขอ B อ่านค่าตอนที่ A ยังไม่ commit จึงเห็น 1 เหมือนกัน · ช่องว่างระหว่าง "เช็ก" กับ "บันทึก" คือที่ที่บั๊กอยู่ · การเอา `if` ไปไว้ใน Go ไม่ช่วย เพราะปัญหาอยู่ที่ **สองคำขออ่านสถานะเดียวกันพร้อมกัน**

## 5. กลไกที่ใช้จริง (อยู่ที่ชั้นข้อมูลทั้งหมด)

| # | กลไก | อยู่ที่ | กันอะไร |
| --- | --- | --- | --- |
| 1 | `UPDATE … WHERE sku = $1 AND available >= $2 RETURNING available` | `backend/internal/store/orders.go:228` | **เช็กกับบันทึกเป็นคำสั่งเดียว** — PostgreSQL ล็อกแถวและประเมิน `WHERE` ใหม่หลังคำขอก่อนหน้า commit คำขอที่สองจึงไม่เจอแถว แล้วได้ `pgx.ErrNoRows` → `409 OUT_OF_STOCK` |
| 2 | `CHECK (available >= 0)` | `schema.sql` ตาราง `products` | ด่านสุดท้าย ถ้ามีใครเขียน query ใหม่ผิดในอนาคต ฐานข้อมูลจะปฏิเสธเอง |
| 3 | `CREATE UNIQUE INDEX one_claim_per_buyer_per_lot ON limited_claims (lot_id, buyer_key) WHERE status IN ('held','paid')` | `schema.sql` | สิทธิ์ "คนละ 1 ใบ" ตอนเปิด 2 แท็บ (BR-31 · `TC-RACE-03`) |
| 4 | `CREATE UNIQUE INDEX one_first_order_coupon ON coupon_redemptions (user_id) WHERE code = 'NEWBIT200' AND status IN ('held','paid')` | `schema.sql` | NEWBIT200 ใช้ซ้ำตอนกดพร้อมกัน (BR-17 · `TC-RACE-04`) |
| 5 | ล็อกแถวเรียงตาม SKU ก่อนเสมอ (`sort.Slice`) | `orders.go:225` | กัน deadlock เมื่อสองออเดอร์มีสินค้าชุดเดียวกันแต่ลำดับต่างกัน |
| 6 | ทั้งหมดอยู่ใน transaction เดียวกับการสร้างออเดอร์ | `orders.go` `PlaceOrder` | ถ้าชิ้นใดไม่พอ ไม่มีออเดอร์เกิดขึ้นเลย (FR-36 · `TC-ORDER-02`) |

**ทำไมต้องเป็นชั้นข้อมูล:** กลไก 1–4 ทำงานแม้คำขอจะมาจากคนละโปรเซส คนละเครื่อง หรือยิงตรงเข้า API โดยไม่ผ่านหน้าเว็บ (`TC-NFR-03`) · ถ้าเช็กใน React หรือใน memory ของ Go จะกันได้แค่ภายใน instance เดียว

## 6. ผลหลังแก้ (โค้ดจริงที่ส่ง)

| N (คำขอพร้อมกัน) | รอบที่เกิดใบซ้ำ / 50 | ใบยืนยันเฉลี่ยต่อรอบ | รอบที่ของติดลบ | เวลาตอบ p50 | p95 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | **0** | 1.00 | 0 | 9 ms | 45 ms |
| 5 | **0** | 1.00 | 0 | 10 ms | 35 ms |
| 10 | **0** | 1.00 | 0 | 15 ms | 101 ms |

ผลจาก Playwright (`npm run test:race`) — 7 ข้อผ่านทั้งหมดใน 49 วินาที

| TC | ผล |
| --- | --- |
| `TC-RACE-01` N = 2 × 50 รอบ | ✅ ผู้แพ้ได้ `409 OUT_OF_STOCK` ครบ 50 ครั้ง |
| `TC-RACE-01` N = 5 × 50 รอบ | ✅ ผู้แพ้ 200 ครั้ง เป็น `OUT_OF_STOCK` ทั้งหมด |
| `TC-RACE-01` N = 10 × 50 รอบ | ✅ ผู้แพ้ 450 ครั้ง เป็น `OUT_OF_STOCK` ทั้งหมด |
| `TC-RACE-03` บัญชีเดียวกัน 2 แท็บ (ของมี 3 ใบ) | ✅ ได้ `201` ใบเดียว อีกอัน `409 LIMIT_REACHED` |
| `TC-RACE-04` NEWBIT200 2 แท็บ | ✅ ได้ `201` ใบเดียว อีกอัน `409 COUPON_USED` |
| `TC-RACE-05` ของ 4 ชิ้น ยิง 10 คำขอ | ✅ สำเร็จพอดี 4 · `available` = 0 |

**เวลาตอบแย่ลงไหม:** ไม่ · p50 ของโค้ดจริง (9–15 ms) **เร็วกว่า** ตัวทดลอง (12–46 ms) ด้วยซ้ำ เพราะยิง query เดียวแทนสอง query · p95 ที่ 101 ms ที่ N = 10 มาจากการรอล็อกแถว ซึ่งเป็นพฤติกรรมที่ถูกต้อง

## 7. ข้อจำกัด · สิ่งที่รายงานนี้ **ไม่** ได้พิสูจน์

| ไม่ได้พิสูจน์ | เพราะอะไร |
| --- | --- |
| เว็บหลาย instance หลัง load balancer | ทดสอบกับ backend container เดียว · แต่กลไกทั้ง 6 อยู่ในฐานข้อมูล จึงใช้ได้กับหลาย instance ตามทฤษฎี — ยังไม่มีหลักฐานการรันจริง |
| ฐานข้อมูลหลายโหนด (replica / failover) | `UPDATE … WHERE` และ unique index การันตีได้ภายใน PostgreSQL โหนดเดียว ยังไม่ได้ทดสอบกับ replica ที่ตามหลัง |
| network ช้าหรือหลุดกลางคัน | client กับ server อยู่บนเครื่องเดียวกัน หน่วงจริงต่ำกว่าสภาพใช้งานมาก · กรณี timeout แล้ว client retry ยังไม่ได้ทดสอบ |
| คนกดพร้อมกันระดับร้อยคน | สูงสุดที่ทดสอบคือ 10 คำขอพร้อมกัน · `MaxConns = 30` ใน `main.go` จะเป็นคอขวดก่อนถึงระดับนั้น |
| เวลาจริงที่ยาวนาน | ใช้นาฬิกาจำลอง (`POST /api/test/clock`) จึงไม่ได้พิสูจน์พฤติกรรมเมื่อระบบรันต่อเนื่องหลายวัน |
