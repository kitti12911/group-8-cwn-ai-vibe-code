## 4. ต้นเหตุ

```text
เวลา →
  คำขอ A:  SELECT available (เห็น 1) ✅ ─────────── UPDATE available = 1 − 1 = 0 ✅ COMMIT
  คำขอ B:        SELECT available (เห็น 1) ✅ ─────────── UPDATE available = 0 − 1 = −1 ✅ COMMIT
                 ↑ ทั้งคู่เห็นว่ายังมีของ เพราะยังไม่มีใคร COMMIT
```

ที่ isolation level `READ COMMITTED` (ค่าตั้งต้นของ PostgreSQL) คำขอ B อ่านค่าตอนที่ A ยังไม่ commit จึงเห็น 1 เหมือนกัน · ช่องว่างระหว่าง "เช็ก" กับ "บันทึก" คือที่ที่บั๊กอยู่ · การเอา `if` ไปไว้ใน Go ไม่ช่วย เพราะปัญหาอยู่ที่ **สองคำขออ่านสถานะเดียวกันพร้อมกัน**

## 5. กลไกที่ใช้จริง (อยู่ที่ชั้นข้อมูลทั้งหมด)

| # | กลไก | อยู่ที่ | กันอะไร |
| --- | --- | --- | --- |
| 1 | `UPDATE … WHERE sku = $1 AND available >= $2 RETURNING available` | `backend/internal/store/orders.go:228` | **เช็กกับบันทึกเป็นคำสั่งเดียว** — PostgreSQL ล็อกแถวและประเมิน `WHERE` ใหม่หลังคำขอก่อนหน้า commit คำขอที่สองจึงไม่เจอแถว แล้วได้ `pgx.ErrNoRows` → `409 OUT_OF_STOCK` |
| 2 | `CHECK (available >= 0)` | `schema.sql` ตาราง `products` | ด่านสุดท้าย ถ้ามีใครเขียน query ใหม่ผิดในอนาคต ฐานข้อมูลจะปฏิเสธเอง |
| 3 | `CREATE UNIQUE INDEX one_claim_per_buyer_per_lot ON limited_claims (lot_id, buyer_key) WHERE status IN ('held','paid')` | `schema.sql` | สิทธิ์ "คนละ 1 ใบ" ตอนเปิด 2 แท็บ (BR-31 · `TC-RACE-03` · `TC-RACE-02b`) |
| 4 | `CREATE UNIQUE INDEX one_first_order_coupon ON coupon_redemptions (user_id) WHERE code = 'NEWBIT200' AND status IN ('held','paid')` | `schema.sql` | NEWBIT200 ใช้ซ้ำตอนกดพร้อมกัน (BR-17 · `TC-RACE-04`) |
| 5 | ล็อกแถวเรียงตาม SKU ก่อนเสมอ (`sort.Slice`) | `orders.go:225` | กัน deadlock เมื่อสองออเดอร์มีสินค้าชุดเดียวกันแต่ลำดับต่างกัน |
| 6 | ทั้งหมดอยู่ใน transaction เดียวกับการสร้างออเดอร์ | `orders.go` `PlaceOrder` | ถ้าชิ้นใดไม่พอ ไม่มีออเดอร์เกิดขึ้นเลย (FR-36 · `TC-ORDER-02`) |

**ทำไมต้องเป็นชั้นข้อมูล:** กลไก 1–4 ทำงานแม้คำขอจะมาจากคนละโปรเซส คนละเครื่อง หรือยิงตรงเข้า API โดยไม่ผ่านหน้าเว็บ (`TC-NFR-03`) · ถ้าเช็กใน React หรือใน memory ของ Go จะกันได้แค่ภายใน instance เดียว

## 7. ชั้นหน้าเว็บ · `TC-RACE-02` · `TC-RACE-02b`

`e2e/race/ui-race.spec.ts` · project `race-ui` (chromium) · `npm run test:race:ui`

| **ผู้แพ้** | ปุ่ม `out-of-stock-remove` มองเห็นได้ | ต้องมี **ทางออก** ให้ลูกค้า ไม่ใช่ทางตัน |
| **ผู้แพ้** | URL ต้อง **ไม่** ตรง `/checkout/` | ข้อที่สำคัญที่สุดของทั้งไฟล์ — ห้ามพาคนที่ไม่ได้ของไปจ่ายเงิน |

`TC-RACE-02b` ใช้เกณฑ์เดียวกัน ยกเว้นข้อความของผู้แพ้ต้องเป็น `จำกัดคนละ 1 ใบ` **ไม่ใช่** "ของหมด" — ถ้าหน้าเว็บโชว์ "ของหมด" ทั้งที่ยังเหลือ 2 ใบ ลูกค้าจะเข้าใจผิดและเลิกซื้อ

### 7.4 ตรวจฝั่งฐานข้อมูลผ่าน API · หน้าเว็บจะโชว์อะไรก็ตาม ของจริงต้องตรง

| ตรวจ | `TC-RACE-02` | `TC-RACE-02b` |
| --- | --- | --- |
| `available('GPU-V57')` | ต้องเป็น **0** และ `>= 0` (ห้ามติดลบ) | ต้องเป็น **2** (ถูกกันแค่ใบเดียว ทั้งที่กด 2 ครั้ง) |

### 7.5 ผู้ชนะสลับกันทุกรอบ

ผู้ชนะ **ไม่คงที่** — รันซ้ำแล้วบางรอบหน้าต่าง A ได้ บางรอบ B ได้ · test จึงไม่ได้เขียนว่า "A ต้องชนะ" แต่เขียนว่า "ต้องมีผู้ชนะพอดี 1" แล้วค่อยหาว่าใครชนะจากผลจริง (`const win = resA === 'WIN' ? pageA : pageB`)

การสลับนี้เป็นหลักฐานว่า **การแข่งเกิดขึ้นจริง** · ถ้าผู้ชนะเป็นหน้าต่างเดิมทุกรอบ แปลว่าจริง ๆ แล้วไม่ได้ยิงพร้อมกัน แค่เรียงคิวกันเฉย ๆ แล้ว test ก็จะไม่ได้ทดสอบอะไรเลย

### 8.1 ทำไม GIF ถึง encode ด้วย JS ล้วน ไม่ใช้ ffmpeg

## 10. race condition ตัวที่สองที่เจอจริง · `BUG-EXPLORE-02`

ชุดนี้เรียก `POST /api/test/reset` ก่อนทุกรอบ (150 รอบที่ชั้น API + ทุก test ที่ชั้นหน้าเว็บ) · ตัว `reset` เองมีบั๊กการแย่งทรัพยากร

| | |
| --- | --- |
| อาการ | `POST /api/test/reset` ตอบ `500` เป็นครั้งคราว หรือค้างเกิน 10 วินาที · log ฝั่งเว็บขึ้น `maintain: commit unexpectedly resulted in rollback` |
| เจอยังไง | ยิง `reset` ติดกัน 1,000 ครั้ง (ระหว่างรัน property P2) |
| ต้นเหตุ | `Store.Reset` ทำ `DROP SCHEMA public CASCADE` ซึ่งต้องใช้ `ACCESS EXCLUSIVE` ทุกตาราง · แต่ `Store.Maintain` วิ่งทุกวินาที (`cmd/server/main.go:67`) **และ** วิ่งก่อนทุก API request (`internal/api/server.go:36`) ในทรานแซกชันของตัวเอง · ไม่มีอะไรกันสองตัวนี้ |
| แก้ | `sync.RWMutex` ใน `Store` — `Maintain` ถือ `RLock` (ยังวิ่งพร้อมกันเองได้) · `Reset` ถือ `Lock` · **แก้ที่ต้นเหตุ ไม่ใช้ retry กลบ** ตาม `TEST-PLAN.md` §2.5 |
| หลังแก้ | ไม่มี error `maintain:` อีกเลย |
| ผลพลอยได้ | P2 เคยเรียก `reset` ทุกเคส ทั้งที่ทุกเคสของ P2 คาดว่าจะ **ถูกปฏิเสธ** จึงไม่เปลี่ยนสถานะอะไรเลย · ย้าย `reset` ออกจากตัว property แล้วชุด property ลดจาก 10.3 นาที เหลือ 1.5 นาที ที่จำนวนเคสเท่าเดิม (~7 เท่า) |

เป็น race คนละรูปแบบกับข้อ 1–7: ไม่ใช่ลูกค้าสองคนแย่งของ แต่เป็น **งานเบื้องหลังชนกับคำสั่งของแอดมิน** · รายละเอียดเต็มอยู่ใน `e2e/triage.json` และ `BUG-HUNT.md` §2.6

## 11. ข้อจำกัด · สิ่งที่รายงานนี้ **ไม่** ได้พิสูจน์

### 11.1 ชั้น API

| ไม่ได้พิสูจน์ | เพราะอะไร |

| เวลาจริงที่ยาวนาน | ใช้นาฬิกาจำลอง (`POST /api/test/clock`) จึงไม่ได้พิสูจน์พฤติกรรมเมื่อระบบรันต่อเนื่องหลายวัน |

### 11.2 ชั้นหน้าเว็บ (เพิ่มจากข้อ 7)

| ไม่ได้พิสูจน์ | เพราะอะไร |
| --- | --- |
| สองเครื่องจริง ๆ | สอง context อยู่ใน Chromium ตัวเดียว เครื่องเดียว · แยก cookie / `localStorage` จริง แต่ยังใช้ network stack และ CPU ร่วมกัน |

| ผู้แพ้กด "เอาชิ้นนี้ออก" แล้วสั่งซื้อต่อจนจบได้ | ตรวจแค่ว่า **ปุ่มมองเห็นได้** ยังไม่ได้ตามต่อว่ากดแล้วจบงานได้จริง |
| ผู้ชนะจ่ายเงินสำเร็จ / ของถูกปล่อยคืนเมื่อหมดเวลากัน | ตรวจแค่ว่า `hold-until` ขึ้นบนจอ · เส้นทางจ่ายเงินและการหมดอายุอยู่ TC อื่น |
| ผู้แพ้กดซ้ำ (กดรัว / retry) | ไม่ได้ทดสอบการกดปุ่มเดิมซ้ำหลังเห็น error |
