### 2.4 ตัวที่พลาด และบทเรียนเรื่อง "ขอบของการจับได้"

**ไม่มีตัวที่พลาด** แต่ตัวเลข 5/5 ถ้าอ่านแค่นั้นจะหลอกตัวเอง — ของจริงคือ

> บั๊ก #1 ทำให้ TC แดง **16 ข้อ** ส่วนบั๊ก #2 #3 #4 #5 แต่ละตัวมี TC จับได้ **ข้อเดียวเป๊ะ**
> ถ้า TC ข้อนั้นข้อเดียวหายไป บั๊กตัวนั้นหลุดทันที · แผนนี้จึงไม่ได้ "แข็งแรง 5/5" แต่ **รอดมา 4 ใบด้วยเส้นยาแดง**

โยงกับผลขั้น 4 (`MUTATION-REPORT.md`) — mutant ที่เคยรอดมีรูปร่างเดียวกับบั๊กที่ฝังจริง

| #2 `G4 >= 3000` → ส่งด่วนฟรี | **S1** · `if q.G4 >= 3000` → `>` และ `3000` → `3001` (`pricing.go:245`) | รอดรอบ 1 · ถูกฆ่าในรอบ 2 ด้วย `TestShippingFreeBoundary` | ถ้าไม่ได้ทำ mutation testing ขั้น 4 ก่อน **บั๊ก #2 น่าจะหลุด** — TC ที่จับได้มาจากการอุดรูที่ S1 ชี้ |

### 2.7 สิ่งที่การซ้อมนี้ **ไม่ได้** พิสูจน์

| ไม่ได้พิสูจน์ | เพราะอะไร |
| --- | --- |
| แผนทนต่อบั๊กที่ "คนนอกทีมจริง ๆ" คิด | Red เป็น agent ในเซสชันเดียวกัน ถูกกันไม่ให้เห็นชุดทดสอบก็จริง แต่ยังอยู่ใต้ผู้ควบคุมคนเดียวกับฝั่ง Blue · ตัวเลข 5/5 จึงต้องอ่านว่าเป็น **ขีดบน** ไม่ใช่ค่าที่ทีมคู่จริงจะวัดได้ |
| การ merge แบบไม่เห็น diff โดยคนนอกทีม | ไม่มีคนนอกทีมมา `git apply` ให้ · ใช้การห้ามอ่านไฟล์แทน ซึ่งอ่อนกว่า |
| ขั้นตอน "ส่งเฉลยให้ผู้สอนเป็น zip มีรหัส" | ยังไม่ได้ทำ เพราะยังไม่มีผู้สอนรับ · ใช้การกันเฉลยออกนอก repo จนล่าเสร็จแทน และพิสูจน์ด้วยลำดับ commit |
| **ผู้ล่าเป็น agent อิสระตลอดกระบวนการ** | agent ที่ตั้งใจให้ล่าแบบตาบอด **ล้ม 3 รอบ** (`API Error: Response stalled mid-stream` 2 ครั้ง แล้ว session limit) · ผู้ควบคุมจึงเป็นคนรันชุดทดสอบเอง · สิ่งที่ยังเชื่อได้คือ **ตัวเลข "TC ไหนแดง" เครื่องเป็นคนตัดสิน ไม่ขึ้นกับว่าใครกดรัน และรันซ้ำได้ด้วยคำสั่งใน §2.8** ส่วนที่อ่อนลงคือคำอธิบายสาเหตุรายตัว ซึ่งผู้ควบคุมเคยเห็นรายงานของ Red มาก่อน |
| ฝังบั๊กให้ทีมคู่ | แพตช์ `BUG_MODE=2` + เฉลยพร้อมส่งแล้ว แต่ยังไม่มีทีมคู่มารับ |
