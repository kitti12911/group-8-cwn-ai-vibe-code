### 2.3 ทำไมชั้นที่สองถึงสำคัญเท่าชั้นแรก

บท 03 T9 **"อย่าอบบั๊ก"** — ถ้า oracle ลอกตรรกะจากเว็บ บั๊กของเว็บจะถูกลอกมาด้วย แล้ว P1 จะ **เขียวตลอดทั้งที่ผิด**
oracle ที่ลอกมาไม่ได้แค่ "ไม่มีประโยชน์" แต่ **อันตรายกว่าไม่มี** เพราะมันออกใบรับรองความถูกต้องปลอม ๆ ให้บั๊ก
เกณฑ์ C ของการบ้านจึงให้ 0 กับ oracle ที่พิสูจน์ความเป็นอิสระไม่ได้ · ตัวเลข 27/27 อย่างเดียวพิสูจน์ไม่ได้ ต้องมีคำตัดสิน INDEPENDENT คู่กัน

## 3. P1 · ผลทั้งสองโหมด

### 3.1 `BUG_MODE=0` — เขียว 1,000 เคส

เทียบ `total` และ `vat` ของเว็บกับ oracle ทุกเคส · seed 2026 · ไม่มีข้อที่ไม่ตรง

อ่านว่า: **ในขอบเขตที่ตัวสุ่มครอบ** (ข้อ 7) เว็บคิดเงินตรงกับเอกสารตามที่ oracle ตีความ · ไม่ได้แปลว่า "ราคาถูกต้องทุกกรณี" (ข้อ 8)

### 3.2 `BUG_MODE=2` — แดง และย่อเคสให้เอง

`fast-check` แดงตั้งแต่เคสที่ **3** แล้วย่อ (shrink) จนเหลือเคสเล็กที่สุดที่ยังพัง

```text
seed: 2026 · path: "2:0:0:0:0:0:1:1"
{ items:[{sku:"CPU-N5",qty:1}], now:"2026-11-12T00:00:00+07:00", user:"C3",
  coupon:undefined, shipping:"standard", assembly:false }
```

ไม่มี flash sale · ไม่มีคูปอง · ไม่มีชุดประกอบ · ของชิ้นเดียว — เหลือตัวแปรเดียวคือ **ระดับสมาชิกของ C3** ซึ่งคือจุดบั๊กพอดี
บั๊กที่ฝัง: **BR-01** ยอดสะสม ฿20,000 พอดีต้องได้ Silver แต่กลายเป็น GENERAL

| | |
| --- | --- |
| ชุด property ที่ `BUG_MODE=2` | 32 ผ่าน · **1 แดง (P1)** — `BUG-HUNT.md` §2.2 |
| TC ที่แดงจากบั๊กตัวนี้ทั้งระบบ | 16 ข้อ รวมทั้ง P1 — `BUG-HUNT.md` §2.3 |
| สิ่งที่ตาราง 27 แถวทำไม่ได้ | ตารางบอกว่า "Q03 ผิด" แต่ไม่บอกว่า **ตัวแปรไหน** เป็นต้นเหตุ · การ shrink บอก |

### 3.3 ขั้นตอนเมื่อ P1 แดง (ใช้จริงแล้วกับเคสข้างบน)

1. คัดลอก input ที่ **ย่อแล้ว** พร้อม seed และ path มาลงรายงาน — ทำแล้ว (ข้อ 3.2)
2. คำนวณด้วยมือ 1 ครั้ง ตัดสินว่าใครผิด: **เว็บ** · **oracle** · หรือ **สมมติฐาน**
3. เว็บผิด → ลง `e2e/triage.json` และเพิ่มเป็น TC ปกติใน `TEST-PLAN.md` · **ห้ามแก้ oracle ให้ตรงเว็บ**
4. oracle ผิด → แก้ oracle แล้วเพิ่มแถวใน `npm run test:oracle`
5. สมมติฐานผิด → เพิ่มคำถามใน `QUESTIONS-TO-OWNER.md` แล้วติดป้าย `[O-ยังไม่ยืนยัน]` ให้ TC ที่กระทบ

ผลของเคส 3.2 คือข้อ 3 (เว็บผิด) · ช่อง `oracleWrong` และ `assumptionWrong` ใน `e2e/triage.json` ยังว่างทั้งคู่

## 4. ทำไม P2–P6 ยังมีค่า **แม้ตอนนี้จะมี oracle แล้ว**

เหตุผลเดิมคือ "P1 ยังรัน​ไม่ได้" ซึ่งหมดไปแล้ว เหตุผลใหม่แข็งกว่าเดิม: **P1 เชื่อได้เท่าที่ oracle เชื่อได้** ส่วน P2–P6 ไม่ต้องเชื่อใครเลย

| property | จับบั๊กแบบที่ P1 จับไม่ได้ | จับไม่ได้เพราะอะไร |
| --- | --- | --- |
| P3 | ตัวเลขในใบสรุปบวกลบไม่ลงตัว (`g1…g4` · `vat + preVat ≠ total` · ผลรวมบรรทัด ≠ `g1`) | P1 ดูแค่ `total` กับ `vat` ถ้า oracle ผิด **ตรงกับเว็บพอดี** P1 เขียว แต่ P3 ยังแดง |
| P4 | กฎส่วนลดเขียนกลับทาง — เพิ่มของแล้วยอดสินค้า **ลดลง** | เป็นความสัมพันธ์ระหว่างสอง input ไม่ใช่ค่าของ input เดียว · oracle ที่ผิดเหมือนกันทั้งสองครั้งก็ยังเขียวที่ P1 |
| P5 | ส่วนลดเกินเพดาน · ยอดติดลบ · ค่าส่ง/ค่าประกอบโผล่ค่าที่ไม่มีในกฎ | เป็นกรอบที่ "ยังไงก็ต้องจริง" แม้ oracle จะคิดเหมือนเว็บทุกประการ |
| P6 | ความไม่ตายตัว — แอบใช้ `time.Now()` · map ที่ลำดับไม่แน่นอน · cache สกปรก | P1 เรียกเคสละครั้งเดียว จึงมองไม่เห็นว่าเรียกซ้ำแล้วเปลี่ยน |
| P2 | ระบบ **รับ** คำขอที่ผิดกฎเงียบ ๆ (ของไม่พอ · sku มั่ว · qty 0 · ส่งด่วนนอกกรุงเทพฯ) | oracle ไม่รู้จักสต็อก เพดานต่อคน หรือจังหวัด (ข้อ 6.1) · P1 ตรวจแต่เงิน ไม่ตรวจสิทธิ์ |

ประโยคที่การบ้านต้องการให้พูดออกมาตรง ๆ: **ถ้า oracle ถูกลอกมาจากเว็บหรือจากอินเทอร์เน็ต P1 จะกลายเป็นศูนย์ทันที** แต่ P2–P6 ยังทำงานเหมือนเดิมทุกข้อ เพราะไม่มีข้อไหนต้องรู้ "ราคาที่ถูก" เลย · การมี oracle จึงเป็นการ **เพิ่ม** ชั้นหนึ่ง ไม่ใช่มาแทนอีกห้าชั้น

### 5.2 `BUG-EXPLORE-02` · reset ชนกับงานเบื้องหลัง maintain

เจอระหว่างรัน P2 ที่ยิง `POST /api/test/reset` ทุกเคส — **ไม่ใช่บั๊กที่ใครฝังไว้ เป็นบั๊กจริงของเว็บ**

| | |
| --- | --- |
| อาการ | `POST /api/test/reset` ตอบ `500` หรือค้างเกิน 10 วินาทีเป็นครั้งคราว · log ขึ้น `maintain: commit unexpectedly resulted in rollback` |
| ทำซ้ำ | ยิง reset ติดกัน 1,000 ครั้ง |
| ต้นเหตุ | `Store.Reset` ทำ `DROP SCHEMA public CASCADE` (ต้องใช้ `ACCESS EXCLUSIVE` lock ทุกตาราง) ขณะที่ `Store.Maintain` วิ่งทุกวินาที (`cmd/server/main.go:67`) **และ** วิ่งก่อนทุก API request (`internal/api/server.go:36`) ในทรานแซกชันของตัวเอง · ไม่มีอะไรกันสองตัวนี้ |
| วิธีแก้ | `sync.RWMutex` ใน `Store` · `Maintain` ถือ `RLock` (ยังวิ่งขนานกันเองได้) · `Reset` ถือ `Lock` — **แก้ที่ต้นเหตุ ไม่ใส่ retry กลบ** ตาม `TEST-PLAN.md` §2.5 |
| ผลหลังแก้ | `maintain:` error = **0** |

บันทึกไว้ที่ `e2e/triage.json` → `BUG-EXPLORE-02` (`status: fixed`) · เขียนเต็มที่ `BUG-HUNT.md` §2.6

## 6. สมมติฐานที่ oracle ต้อง **เดา** และข้อขัดกันที่มันเจอในเอกสารของทีมเอง

ส่วนนี้คือของที่การบ้านให้คะแนน — oracle ที่ "ผ่านหมด" โดยไม่รายงานว่าตัวเองเดาอะไรไว้บ้าง เชื่อถือไม่ได้

## 7. การออกแบบตัวสุ่ม

```ts
const arbCase = fc.record({
  items:    arbCart,                                   // 1–4 บรรทัด · จำนวน 1–3 และไม่เกินของที่มีจริง
  now:      arbNow,                                    // 12–14 พ.ย. ทุกครึ่งชั่วโมง (ครอบทั้งใน/นอก flash sale)
  user:     fc.constantFrom('C1','C2','C3','C4','C5','C11'),  // ไม่ล็อกอิน + ครบ 4 ระดับสมาชิก
  coupon:   fc.constantFrom(undefined,'NEWBIT200','GAMER5','OLD2025','ไม่มีโค้ดนี้'),
  shipping: fc.constantFrom('standard','express','pickup'),
  assembly: fc.boolean(),
});
```

| ตัวแปร | ทำไมสุ่มแบบนี้ |
| --- | --- |
| เวลา ทุกครึ่งชั่วโมง 3 วัน | ครอบ **ขอบ flash sale** (12:00 · 13:00) และวันที่ไม่ใช่ศุกร์ ซึ่งเป็นที่ที่บั๊ก `BUG_MODE=1` #1 ซ่อนอยู่ |
| ลูกค้าครบทุกระดับ **รวมคนไม่ล็อกอิน** | บั๊ก `BUG_MODE=1` #2 และบั๊ก `BUG_MODE=2` #1 มองไม่เห็นเลยถ้าสุ่มแต่ลูกค้าทั่วไป · C3 (ยอดสะสม ฿20,000 พอดี) คือตัวที่ P1 ย่อลงไปเจอ |
| คูปองรวม "โค้ดมั่ว" และโค้ดหมดอายุ | ทางที่ถูกปฏิเสธต้องถูกตรวจเท่า ๆ กับทางที่สำเร็จ |

| ตะกร้าไม่เกิน 4 บรรทัด | ทำให้เคสเล็กและอ่านง่ายตอน shrink · **แลกมาด้วยข้อ 6.2** — ไปไม่ถึงเงื่อนไข 7 หมวด |

## 9. วิธีรันซ้ำ

ต้องมีเว็บรันอยู่ก่อน (`docker compose up -d`)

```bash
cd e2e && npm ci
npm run test:oracle                        # ตรวจ oracle กับตาราง quote 27 แถว → 27 ผ่าน
npm run test:property                      # 27 oracle + 6 property × 1,000 → 33 ผ่าน · ~1.5 นาที
SEED=1234 RUNS=200 npm run test:property   # เปลี่ยน seed หรือลดจำนวนตอนพัฒนา
```

บนเครื่องนี้ (Windows PowerShell) ใช้บรรทัดเดียวแบบนี้แทน

```powershell
cd e2e; npm run test:property
cd e2e; $env:SEED='1234'; $env:RUNS='200'; npm run test:property
```

ทำซ้ำผล P1 แดงที่ `BUG_MODE=2` ตาม `BUG-HUNT.md` §2.8

```bash
BUG_MODE=2 docker compose up -d --build backend

docker compose up -d --build backend        # กลับเป็นโหมดปกติ
```

seed เดิม + `RUNS` เดิม = ชุด input เดิมทุกครั้ง · ถ้าผลต่างออกไป แปลว่า **เว็บเปลี่ยน** ไม่ใช่ test เปลี่ยน
