## 2. ทำไม P2–P6 ยังมีค่าแม้ยังไม่มี oracle

P1 ต้องรู้ "ราคาที่ถูก" จึงเทียบได้ แต่อีก 5 ข้อ **ตรวจได้โดยไม่ต้องรู้กฎเงินเลย** และจับบั๊กคนละชนิดกับ P1

| property | จับบั๊กแบบที่ P1 จับไม่ได้ |
| --- | --- |
| P3 | ถ้า oracle ผิด**ตรงกับเว็บพอดี** P1 จะเขียว แต่ถ้าตัวเลขในใบสรุปบวกลบไม่ลงตัว P3 ยังแดงอยู่ดี |
| P4 | ถ้ากฎส่วนลดเขียนกลับทาง (ซื้อเยอะแล้วถูกลงจนติดลบ) P4 จับได้โดยไม่ต้องรู้ราคาที่ถูก |
| P5 | จับ "ส่วนลดเกินเพดาน" และ "ยอดติดลบ" ได้แม้ oracle จะคิดเหมือนเว็บทุกประการ |
| P6 | จับความไม่ตายตัว (ใช้ `time.Now()` แอบ ๆ หรือ map ที่ลำดับไม่แน่นอน) ซึ่ง P1 ที่เรียกครั้งเดียวจับไม่ได้ |
| P2 | จับ "ระบบรับคำขอที่ผิดกฎเงียบ ๆ" ซึ่งเป็นบั๊กเชิงพฤติกรรม ไม่ใช่เชิงตัวเลข |

## 3. การออกแบบตัวสุ่ม

```ts
const arbCase = fc.record({
  items:    arbCart,                                   // 1–4 บรรทัด · จำนวนไม่เกินของที่มีจริง
  now:      arbNow,                                    // 12–14 พ.ย. ทุกครึ่งชั่วโมง (ครอบทั้งใน/นอก flash sale)
  user:     fc.constantFrom('C1','C2','C3','C4','C5','C11'),  // ไม่ล็อกอิน + ครบ 4 ระดับสมาชิก
  coupon:   fc.constantFrom(undefined,'NEWBIT200','GAMER5','OLD2025','ไม่มีโค้ดนี้'),
  shipping: fc.constantFrom('standard','express','pickup'),
  assembly: fc.boolean(),
});
```

| ตัวแปร | ทำไมสุ่มแบบนี้ |
| --- | --- |
| เวลา ทุกครึ่งชั่วโมง 3 วัน | ครอบ **ขอบ flash sale** (12:00 · 13:00) และวันที่ไม่ใช่ศุกร์ ซึ่งเป็นที่ที่บั๊ก `BUG_MODE=1` #1 ซ่อนอยู่ |
| ลูกค้าครบทุกระดับ **รวมคนไม่ล็อกอิน** | บั๊ก `BUG_MODE=1` #2 มองไม่เห็นเลยถ้าสุ่มแต่ลูกค้าทั่วไป |
| คูปองรวม "โค้ดมั่ว" และโค้ดหมดอายุ | ทางที่ถูกปฏิเสธต้องถูกตรวจเท่า ๆ กับทางที่สำเร็จ |
| จำนวนไม่เกินของที่มีจริง | ไม่งั้นเกือบทุกแบบจะจบที่ `OUT_OF_STOCK` แล้วไม่ได้ทดสอบกฎเงินเลย |

## 4. ⏳ P1 · ทำไมยังไม่รัน

กติกาขั้น 3.1 ของการบ้านบังคับว่า oracle ต้องเขียนจาก `INTERVIEW.md` + `REQUIREMENTS.md` + สมมติฐานขั้น 1 **เท่านั้น** และ **ห้ามให้ AI ที่มีโค้ดเว็บอยู่ในบริบทเป็นคนเขียน** เพราะถ้า oracle ลอกตรรกะมาจากเว็บ บั๊กจะถูกคัดลอกมาด้วย แล้ว P1 จะเขียวตลอดทั้งที่ผิด (บท 03 T9 "อย่าอบบั๊ก") และเกณฑ์ C จะได้ 0

| สิ่งที่เตรียมไว้แล้ว | ที่ไหน |
| --- | --- |
| โครง type และ signature ของ oracle | `e2e/property/oracle/price.ts` (ยังโยน error · `ORACLE_READY = false`) |
| P1 ที่พร้อมรันทันทีที่ `ORACLE_READY = true` | `e2e/property/price.property.spec.ts` ข้อสุดท้าย (ตอนนี้ `skip`) |
| ชุดตรวจ oracle ก่อนใช้งาน | ตาราง quote 27 แถวใน `lib/data.ts` → `npm run test:oracle` |
| พรอมต์สำหรับเซสชันใหม่ | `prompts/05-oracle-independent.txt` |

**ขั้นตอนที่เหลือ:** เปิด Claude Code เซสชันใหม่ที่เห็นแค่เอกสาร → วางพรอมต์ → เอาไฟล์ที่ได้มาวางทับ → `npm run test:oracle` ต้องผ่าน 27/27 → ตั้ง `ORACLE_READY = true` → `SEED=2026 npm run test:property`

เมื่อ P1 มีข้อที่ไม่ตรง ให้ทำตามนี้ก่อนแก้โค้ดใด ๆ

1. คัดลอก input ที่ fast-check **ย่อแล้ว (shrink)** พร้อม seed มาลงรายงานนี้
2. คำนวณด้วยมือ 1 ครั้ง ตัดสินว่าใครผิด: **เว็บ** · **oracle** · หรือ **สมมติฐาน**
3. เว็บผิด → ลง `e2e/triage.json` เป็นบั๊ก และเพิ่มเป็น TC ปกติใน `TEST-PLAN.md` · **ห้ามแก้ oracle ให้ตรงเว็บ**
4. oracle ผิด → แก้ oracle แล้วเพิ่มแถวใน `npm run test:oracle`
5. สมมติฐานผิด → เพิ่มคำถามใน `QUESTIONS-TO-OWNER.md` แล้วติดป้าย `[O-ยังไม่ยืนยัน]` ให้ TC ที่กระทบ
