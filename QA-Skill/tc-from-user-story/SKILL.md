# เขียน test case จาก user story (tc-from-user-story)

ทำเหมือน QA ที่ได้เอกสาร requirement มาก่อน dev เขียนโค้ด: เห็นแค่ **user story + เกณฑ์ยอมรับ + คำถามค้าง (Q) + เรื่องขัดกัน (K)**
ผลสุดท้าย: `TEST-CASES.md` ข้างไฟล์ user story (หรือ path ที่ผู้ใช้บอก) + สรุป coverage

สคริปต์อยู่ที่ `~/.claude/skills/tc-from-user-story/scripts/` ใช้ Node ≥ 18 ไม่มี dependency
**เรียกสคริปต์ด้วย path เต็มเสมอ ห้ามตั้งตัวแปร shell** (`$SKILL_DIR`, `S=...`) เพราะระบบตรวจสิทธิ์จะบล็อกคำสั่งที่มีตัวแปร · ถ้า skill ติดตั้งในโปรเจกต์ ใช้ `.claude/skills/tc-from-user-story/scripts/` แทน

## 🔒 กติกา (ห้ามละเมิด)

1. **ผลที่คาดหวังมาจากเกณฑ์ยอมรับเท่านั้น** ห้ามดูเว็บจริงหรือโค้ดแล้วเขียนผลที่คาดหวังตามที่ระบบทำอยู่ — ถ้าเกณฑ์บอกว่า "ลองจริง ❌" ผลที่คาดหวังยังเป็นตามเกณฑ์ ไม่ใช่ตามที่เว็บทำ (อย่าอบบั๊กลงในผลที่คาดหวัง)
2. **ห้ามแต่งตัวเลข/ข้อความใหม่** ค่าที่ไม่มีในเอกสาร ให้ใส่ `TBD (Qx)` และผูกกับคำถามที่มีอยู่ หรือเพิ่มคำถามใหม่ในหัวข้อ "คำถามใหม่จาก QA" — ห้ามเดาค่าที่ทำให้ test ผ่านง่ายขึ้น
   - คำถามใหม่ใช้รหัส **`QA1`, `QA2`, …** ห้ามต่อเลข Q ของเอกสาร (Q26 อาจชนกับคำถามที่เจ้าของเอกสารเพิ่มทีหลัง)
3. **เกณฑ์ที่ขึ้นกับ Q/K ที่ยังไม่มีคำตอบ** → เขียน test ตามความหมายตรงตัวอักษรที่สุด, ใส่คอลัมน์ "ขึ้นกับ" = `Q1` / `K1`, และระบุใน "หมายเหตุ" ว่าถ้าคำตอบเป็นอีกแบบ ผลที่คาดหวังจะเปลี่ยนเป็นอะไร
   - ถ้าเกณฑ์อ้าง Q/K แต่ TC ข้อนี้ไม่ได้แตะส่วนนั้นจริง ใส่ `ไม่เกี่ยว:K7` ในคอลัมน์ "ขึ้นกับ" + เหตุผลหนึ่งประโยคในหมายเหตุ (ห้ามปล่อยคำเตือนค้างแล้วอธิบายท้ายไฟล์แทน)
4. **แยกที่มาของค่า**: `[เว็บ]` = ร้านประกาศเอง (ยึดได้) · `(ทีมเสนอ)` = ยังไม่ยืนยัน → ใส่ป้าย `⚠️ ทีมเสนอ` ในหมายเหตุของ TC นั้น
5. **ทุกเกณฑ์ยอมรับต้องมีอย่างน้อย 1 TC** ถ้าทดสอบไม่ได้ (เช่น "ใช้ง่าย", "รวดเร็ว" ไม่มีตัวเลข) ให้จดใน "เกณฑ์ที่ทดสอบไม่ได้" พร้อมเสนอวิธีวัด ห้ามข้ามเงียบ ๆ
6. ห้ามแก้ไฟล์ user story ต้นฉบับ

## ขั้นตอน

### 1 · อ่าน story → stories.json
```bash
node ~/.claude/skills/tc-from-user-story/scripts/parse-stories.mjs <ไฟล์ USER-STORIES.md> > stories.json
```
ได้ US ทุกข้อ (รหัส ชื่อ ความสำคัญ เกณฑ์ยอมรับ แต่ละข้ออ้าง Q/K อะไร ที่มา `[เว็บ]`/`(ทีมเสนอ)`), รายการ Q และ K
- ถ้าสคริปต์หา US หรือเกณฑ์ยอมรับไม่เจอ (`stories: 0`) → เอกสารใช้รูปแบบอื่น ถามผู้ใช้ อย่าเดาโครงสร้าง
- ถ้าผู้ใช้ระบุขอบเขต (เช่น "เฉพาะหมวด C" / "เฉพาะ Must") ทำเฉพาะส่วนนั้น และบอกในหัวรายงาน

### 2 · ออกแบบ scenario ต่อ US
1 US = 1 กลุ่ม scenario (`TS-<US>`) · ไล่เกณฑ์ยอมรับทีละข้อ เลือกเทคนิคตาม [references/test-design.md](references/test-design.md)
- มีตัวเลข/เกณฑ์ขั้น (5,000 บาท, 7 วัน, 17:00) → **Boundary Value** ทั้ง ต่ำกว่า/พอดี/สูงกว่า
- มีหลายกลุ่มอินพุต (ตัวเล็ก/ตัวใหญ่, มี/ไม่มีของ) → **Equivalence Partitioning**
- มีหลายเงื่อนไขรวมกัน (จ่ายปลายทาง × By Order × ยอด) → **Decision Table**
- มีสถานะเปลี่ยน (สั่ง → จ่าย → ส่ง → คืน) → **State Transition**
- ทุก US ต้องมี **Negative** อย่างน้อย 1 ข้อ ถ้าเกณฑ์พูดถึงกรณีผิดพลาด

### 3 · เขียน TEST-CASES.md ตาม [references/tc-template.md](references/tc-template.md)
- รหัส `TC-<US เลข>-<ลำดับ 2 หลัก>` เช่น `TC-16-03`
- ระดับ: Must → `P1` · Should → `P2` · Could → `P3`
- ข้อมูลทดสอบเป็นค่าจริงที่ใช้ได้ทันที (`4,999 บาท`, `rtx 5060`) ไม่ใช่ "ยอดที่ต่ำกว่าเกณฑ์"
- **ยอดเงิน = ระบุสินค้า × จำนวน ที่รวมได้ตรงยอด** เช่น `คีย์บอร์ด 1,890 × 1 + เมาส์ 990 × 1 + แผ่นรองเมาส์ 2,121 × 1 = 5,001` ห้ามเขียนแค่ "สินค้ายอดรวม 5,001 บาท" · ถ้าไม่รู้ราคาสินค้าจริง ใช้ราคาสมมติแล้วใส่ `(ราคาสมมติ หาสินค้าจริงที่รวมได้ยอดนี้ก่อนรัน)`
- ผลที่คาดหวังต้อง **ตรวจได้ด้วยตา/assertion** (ข้อความ ตัวเลข สถานะปุ่ม) ไม่ใช่ "ระบบทำงานถูกต้อง"
- ขั้นตอนเป็นเลขข้อ คนที่ไม่เคยเห็นเว็บทำตามได้

### 4 · ตรวจ coverage (สคริปต์ ห้ามนับเอง)
```bash
node ~/.claude/skills/tc-from-user-story/scripts/check-coverage.mjs stories.json TEST-CASES.md            # ทั้งไฟล์
node ~/.claude/skills/tc-from-user-story/scripts/check-coverage.mjs stories.json TEST-CASES.md --priority Must   # ถ้าผู้ใช้สั่งเฉพาะบางส่วน (หรือ --us US-15,US-16)
```
- exit 1 = มีเกณฑ์ยอมรับ **Must** ที่ไม่มี TC หรือ TC อ้าง US/AC ที่ไม่มีจริง → แก้ให้ครบแล้วรันใหม่
- คำเตือน (exit 0) = เกณฑ์ Should/Could ที่ไม่มี TC, เกณฑ์ที่อ้าง Q/K แต่ TC ไม่ได้ใส่ "ขึ้นกับ" → แก้หรืออธิบายในรายงาน
- คัดตาราง coverage ที่สคริปต์พิมพ์ออกมาใส่ท้าย TEST-CASES.md ตรง ๆ ห้ามแก้ตัวเลขมือ

### 5 · สรุปให้ผู้ใช้ (ภาษาไทย)
- จำนวน US / เกณฑ์ยอมรับ / TC (แยก P1–P3 และ Positive/Negative/Boundary) จากผลสคริปต์
- **TC ที่ผลที่คาดหวังยังขึ้นกับคำถามค้าง**: จำนวน + Q ไหนกระทบ TC มากที่สุด (ให้ผู้ใช้รู้ว่าควรไปถามร้านข้อไหนก่อน)
- เกณฑ์ที่ทดสอบไม่ได้ + คำถามใหม่จาก QA
- จุดที่ตัดสินใจเองรอบนี้ (ดู [references/decisions.md](references/decisions.md)) และการละเมิดกติกาใด ๆ บอกตรง ๆ
- path เต็มของ TEST-CASES.md
